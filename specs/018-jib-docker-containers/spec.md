# Feature Specification: Rely on Jib Container Images in Docker Compose

**Feature Branch**: `018-jib-docker-containers`  
**Created**: 2026-09-18  
**Status**: Draft  
**Input**: User description: "docker containers - In 'docker-compose.apps.yaml' the images are built from 'docker/Dockerfile.service'. We have the jib plugin in Maven configured, that is supposed to build the image. Ideally those images should be used in the docker-compose instead of building them; docker-compose should use the images built with jib Lets investigate if that is possible, and if so, rely in jib"

## Clarifications

### Session 2026-09-18
- Q: How should `docker-compose.apps.yml` specify the image tags for the microservices built with Jib? → A: Dual tagging (`${project.version}` and `latest`) generated by Jib, with `docker-compose.apps.yml` referencing `springboot-rube-goldberg/<service>:${IMAGE_TAG:-latest}`.
- Q: What should be done with the legacy `docker/Dockerfile.service` file now that Docker Compose relies on Jib? → A: Remove `docker/Dockerfile.service` entirely to enforce a single, unified container build mechanism via Jib.
- Q: How should developers and CI pipelines invoke the reactor-wide container build across all 8 microservices? → A: Direct Maven goal invocation via `./mvnw compile jib:dockerBuild -DskipTests`, natively executing across the reactor with non-runnable modules skipped via POM configuration.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Run Application Services via Jib-Built Images (Priority: P1) 🎯 MVP

As a developer or operator running the local platform,  
I want `docker-compose.apps.yml` to run container images built by the build tool's containerization plugin (Jib) rather than building them from a custom Dockerfile on every compose invocation,  
so that container startup is fast, reproducible, and decoupled from ad-hoc Dockerfile build contexts.

**Why this priority**: Directly addresses the core user requirement to eliminate redundant Dockerfile builds in Compose and standardize on the preconfigured Jib container images.

**Independent Test**: Build the container images using the project's build tool (`./mvnw compile jib:dockerBuild`), then execute `docker compose` with `docker-compose.apps.yml`. Verify that all 8 application microservices start up successfully and report healthy status without executing Dockerfile build steps.

**Acceptance Scenarios**:

1. **Given** container images have been built by the build tool for all microservices, **When** starting the application stack via Compose (`docker-compose.apps.yml`), **Then** Compose pulls/launches the pre-built container images directly without triggering local Dockerfile builds.
2. **Given** any of the 8 application microservices, **When** inspected in the running Compose environment, **Then** the running container image matches the designated repository and version tag produced by the build tool.
3. **Given** the application stack is launched from the container images, **When** health checks and inter-service endpoints are queried (e.g., Gateway on port 8080), **Then** all services respond identically to the standard runtime environment.

### User Story 2 - One-Step Container Image Generation for All Microservices (Priority: P2)

As a developer adding or updating features across the microservices reactor,  
I want a simple, standardized command to build all application container images into the local container runtime in one step,  
so that I don't have to manually containerize each service individually or worry about bytecode/class version incompatibilities.

**Why this priority**: Streamlines the developer experience so that updating and rebuilding images for all 8 microservices is friction-free, deterministic, and compatible with the project's Java 26 runtime.

**Independent Test**: Run the reactor-wide container build command from the repository root, then inspect the local container image list to confirm that fresh images exist for all 8 application microservices with expected tags.

**Acceptance Scenarios**:

1. **Given** changes in one or more microservices, **When** executing the reactor container build command, **Then** container images for all runnable services are generated and registered in the local container daemon without manual configuration per service.
2. **Given** the library module `common/event-contracts` or the parent POM, **When** the container build command runs, **Then** non-runnable/library modules are cleanly skipped without failing the build.
3. **Given** the project runtime environment (Java 26 bytecode), **When** containerizing each microservice, **Then** entrypoint detection and layer packaging succeed without bytecode inspection errors.

### Edge Cases

- **Missing Local Images**: What happens if a developer runs `docker compose` without first building the images via Jib? Compose should fail fast with a clear missing image error rather than falling back to an obsolete Dockerfile build.
- **Library Module Containerization**: How does the container build handle non-runnable submodules (`common/event-contracts` and root POM)? Non-application modules must have containerization disabled or skipped cleanly.
- **Port and Resource Limits Parity**: Do containers launched from Jib images respect the same memory limits (`mem_limit: 512m`) and JVM tuning (`JAVA_TOOL_OPTIONS`) configured in Compose? Yes, environment variables defined in Compose must continue to configure JVM memory and active profiles seamlessly.
- **Image Tag Synchronization**: What happens when the project version changes (e.g., `1.0.0-SNAPSHOT` vs custom tag)? The Compose image reference should use consistent tagging aligned with the project version or an easily overridable tag variable.
- **Local Daemon vs Registry Authentication**: When executing `jib:dockerBuild`, Jib builds and loads images directly into the local Docker socket/daemon without requiring remote registry authentication or Docker Hub login.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST configure the build tool containerization plugin (Jib) across all 8 runnable application microservices (`gateway`, `customer-service`, `restaurant-service`, `availability-service`, `reservation-service`, `waiting-list-service`, `notification-service`, `analytics-service`).
- **FR-002**: The system MUST bypass bytecode inspection incompatibilities on modern runtimes (Java 26) by explicitly declaring each application's main class in the build configuration.
- **FR-003**: The system MUST skip container image generation for the root aggregator POM and shared library modules (e.g., `common/event-contracts`).
- **FR-004**: `docker-compose.apps.yml` MUST reference the pre-built container images produced by Jib instead of building from `docker/Dockerfile.service`.
- **FR-005**: `docker-compose.apps.yml` MUST maintain all existing environment variables (including `SPRING_PROFILES_ACTIVE=docker` and `JAVA_TOOL_OPTIONS`), port mappings, volume mounts, dependencies, and memory constraints for each service.
- **FR-006**: The system MUST support native reactor-wide containerization via `./mvnw compile jib:dockerBuild -DskipTests` from the project root, automatically containerizing all 8 runnable services and skipping non-runnable modules.
- **FR-007**: The system MUST produce image tags adhering to the consistent naming schema `springboot-rube-goldberg/<service-name>:<version>` as well as `latest` (dual-tagged), and `docker-compose.apps.yml` MUST reference `springboot-rube-goldberg/<service-name>:${IMAGE_TAG:-latest}`.
- **FR-008**: Project documentation (README and architecture guides) MUST document the revised build-and-run workflow using Jib and Docker Compose.
- **FR-009**: The system MUST remove `docker/Dockerfile.service` (and remove the `docker/` directory if empty) and eliminate any build references to it in Docker Compose configurations.

---

### Key Entities *(include if feature involves data)*

- **Container Image**: An OCI-compliant layered image containing the base JRE, application dependencies, resources, and class files, tagged as `springboot-rube-goldberg/<service-name>:<version>`.
- **Application Compose Service**: A service definition within `docker-compose.apps.yml` specifying the container image, networking, dependencies, and runtime environment configuration for one of the microservices.
- **Main Class Declaration**: The explicit fully-qualified class name of the Spring Boot entrypoint for each service module, ensuring deterministic startup without bytecode scanning.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All 8 microservice container images can be generated and loaded into the local container daemon in under 45 seconds on an incremental build.
- **SC-002**: `docker compose -f infrastructure/docker-compose.yml -f infrastructure/docker-compose.apps.yml up` starts 100% of application services using Jib images without triggering any Dockerfile builds.
- **SC-003**: 100% of health probes (`/actuator/health`) across all 8 application microservices report healthy (`UP`) when running from Jib images.
- **SC-004**: The total image size of each microservice is reduced or remains comparable to the Dockerfile-based images while benefiting from fine-grained OCI layer caching.

---

## Assumptions

- The host environment has a running Docker daemon (or compatible OCI container runtime) accessible to Jib when executing `jib:dockerBuild`.
- All 8 application microservices share the same base runtime (`eclipse-temurin:26-jre-alpine`).
- Docker Compose v2 is available in the user environment.
- Any JVM heap limits set via Compose environment (`JAVA_TOOL_OPTIONS`) are respected by the JVM entrypoint created by Jib.
- Jib builds images for the architecture matching the local Docker daemon environment (e.g. `linux/arm64` on Apple Silicon, `linux/amd64` on standard x86_64 CI/CD runners), ensuring local runtime compatibility.
