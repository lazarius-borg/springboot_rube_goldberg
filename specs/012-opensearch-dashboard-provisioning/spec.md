# Feature Specification: OpenSearch Dashboard Provisioning

**Feature Branch**: `012-opensearch-dashboard-provisioning`  
**Created**: 2026-09-15  
**Status**: Draft  
**Input**: User description: "opensearch dashboard provisioning - OpenSearch dashboard should be provisioned in the docker-compose setup so that when OpenSearch Dashboards UI is opened, dashboards where logs and traces from the services are displayed."

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Out-of-the-Box Application Logs Dashboard (Priority: P1)

As a software engineer or platform operator,  
I want OpenSearch Dashboards to come pre-configured with a comprehensive Application Logs Dashboard and index pattern immediately upon startup,  
So that I can search, filter, and inspect service logs, error levels, and execution timestamps across all platform microservices without manual configuration.

**Why this priority**: Logs are the primary diagnostic tool developers rely on during local execution. Having immediate visual access to formatted, filterable logs saves onboarding time and eliminates manual index pattern setup.

**Independent Test**: Start the infrastructure with Docker Compose, open OpenSearch Dashboards at `http://localhost:5601`, navigate to Dashboards, and verify the "Application Logs Dashboard" renders log counts, severity breakdowns, and a log stream table without manual import steps.

**Acceptance Scenarios**:

1. **Given** a fresh environment startup, **When** a user navigates to OpenSearch Dashboards, **Then** the `otel-logs*` index pattern and "Application Logs Dashboard" are already present and operational.
2. **Given** microservices emitting structured logs, **When** a user views the Application Logs Dashboard, **Then** visual panels display log volume over time, log counts segmented by severity (INFO, WARN, ERROR), distribution by service name, and an interactive log table.
3. **Given** the log search table, **When** a user clicks a specific service name or filters by severity, **Then** all visual panels and table rows update to show only matching log events.

---

### User Story 2 - Out-of-the-Box Distributed Traces Dashboard & Visualization (Priority: P2)

As a software engineer troubleshooting latency or distributed transactions,  
I want OpenSearch Dashboards to provide a pre-provisioned Distributed Traces Dashboard and pre-configured trace index pattern,  
So that I can explore transaction spans, service call hierarchies, error counts, and latency metrics across the microservice ecosystem.

**Why this priority**: Distributed tracing is crucial for end-to-end transaction visibility across microservices. Automated trace dashboards allow developers to inspect multi-hop workflows without constructing complex queries manually.

**Independent Test**: Trigger a request through API Gateway, open the pre-provisioned Traces Dashboard, and verify transaction span counts, latency histograms, and span attributes are displayed accurately.

**Acceptance Scenarios**:

1. **Given** OpenSearch Dashboards is launched, **When** navigating to the Dashboards section, **Then** a "Distributed Traces Dashboard" is available and connected to the trace data stream (`ss4o_traces-*`).
2. **Given** traces generated by microservice HTTP and Kafka flows, **When** viewing the Traces Dashboard, **Then** panels display span duration histograms, total span throughput, status code distributions (OK vs ERROR), and a list of recent distributed traces.
3. **Given** a trace record with a specific Trace ID, **When** clicking or filtering by that Trace ID, **Then** developers can correlate and inspect all spans associated with that single end-to-end transaction.

---

### User Story 3 - Automated Provisioning Lifecycle & Zero-Touch Deployment (Priority: P3)

As a developer spinning up or restarting the platform infrastructure,  
I want the dashboard provisioning process to execute automatically, reliably, and idempotently in the background,  
So that all saved objects (dashboards, visualizations, index patterns) are ready when the UI becomes reachable, without duplicate assets created on subsequent restarts.

**Why this priority**: Manual setup steps are error-prone and hinder team velocity. An idempotent automated provisioning process guarantees deterministic developer environments.

**Independent Test**: Run `docker compose down` and `docker compose up -d` repeatedly; verify OpenSearch Dashboards starts with all assets intact, without throwing errors or creating duplicate dashboard entries.

**Acceptance Scenarios**:

1. **Given** `docker compose up -d` is executed, **When** the OpenSearch Dashboards container finishes starting, **Then** all dashboards and index patterns are already imported and ready for immediate use.
2. **Given** the infrastructure is restarted or updated, **When** the provisioning mechanism runs again, **Then** it updates existing objects or cleanly skips re-creation without producing duplicate dashboard entries.
3. **Given** OpenSearch backend or Dashboards server is still initializing, **When** the provisioning wrapper begins, **Then** it waits resiliently for Dashboards to report a healthy status before attempting object creation.

---

### Edge Cases

- **Zero Ingested Data at Startup**: When OpenSearch Dashboards is opened before any microservices have emitted logs or traces, the dashboards must display empty-state indicators rather than fatal rendering errors.
- **Backend Availability Lag & Unresponsive Container Handling**: OpenSearch and Dashboards may take 15–30 seconds to initialize. The provisioning wrapper must poll `/api/status` resiliently (2-second intervals, up to 30 attempts). The loop must distinguish between initializing states (HTTP 503 or status `red` where it logs status and continues retrying) versus connection failure or completely unresponsive container, logging attempt numbers and aborting after the 60-second threshold if readiness is never reached.
- **Container Reboots**: Multiple `docker compose restart` cycles must remain idempotent and never create `(1)` duplicate objects or overwrite customized saved searches.
- **Index Pattern Matching**: Index patterns must cleanly encompass both current and future daily indices or data streams (e.g., `otel-logs*` and `ss4o_traces-*`).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The platform MUST automatically provision an index pattern for application logs (`otel-logs*`) configured with `@timestamp` / `timestamp` as the primary time attribute upon environment startup.
- **FR-002**: The platform MUST automatically provision an index pattern for distributed trace data (`ss4o_traces-*`) configured with `startTime` as the primary time attribute upon environment startup.
- **FR-003**: The platform MUST provision a centralized "Application Logs Dashboard" featuring:
  - A timeline histogram of log event volume.
  - A breakdown chart of log records by severity level (INFO, WARN, ERROR).
  - A breakdown chart of log records by originating service name.
  - A structured log stream table displaying timestamp, service name, severity, traceId, and log message with expandable detail views.
- **FR-004**: The platform MUST provision a "Distributed Traces Dashboard" featuring:
  - Total trace span volume and throughput over time.
  - Status breakdown displaying successful vs failed operations.
  - Duration/latency distribution across service operations.
  - A table of recent traces showing traceId, operation name, service name, duration, and status.
- **FR-005**: All dashboards, visualizations, and index patterns MUST be provisioned automatically via Docker Compose without requiring any manual export/import steps from the user. The background provisioning execution MUST terminate cleanly immediately upon successful saved objects import (`success: true`), and MUST NOT crash or terminate the primary OpenSearch Dashboards process if provisioning encounters an error or timeout.
- **FR-006**: The dashboard provisioning mechanism MUST be idempotent; restarting the Docker Compose infrastructure MUST NOT duplicate or corrupt provisioned saved objects. If the Saved Objects import API returns partial errors (where `errors` array is non-empty), the provisioning process MUST output the complete error payload to container logs and report failure rather than treating partial imports as successful.
- **FR-007**: The provisioning mechanism MUST wait for OpenSearch and OpenSearch Dashboards to become healthy (evaluating Dashboards' internal status endpoint at `http://localhost:5601/api/status` for state `green` or `yellow`, confirming backend OpenSearch readiness) before executing provisioning operations.
- **FR-008**: The platform MUST provision a total of three structured dashboards:
  1. A "Platform Observability Overview" dashboard aggregating top-level system health metrics, error rates, and total transaction activity.
  2. An "Application Logs Dashboard" dedicated to deep microservice log stream search, severity breakdowns, and structured field filtering.
  3. A "Distributed Traces Dashboard" dedicated to end-to-end request latency percentiles, error breakdowns, and individual span inspections.
- **FR-009**: OpenSearch Dashboards MUST be configured to designate the "Application Logs Dashboard" as the default landing route, so that navigating to the root application URL (`http://localhost:5601`) immediately opens the live microservice log view with zero required navigation clicks.
- **FR-010**: All provisioned dashboards MUST be pre-configured with a default time window of the "Last 15 minutes" (`now-15m` to `now`) and an active auto-refresh interval of 10 seconds, delivering an immediate live-tail monitoring experience for running services.

### Clarifications & Decisions

#### Session 2026-09-15
- **Q1: Dashboard Organization**: User selected Option B. The provisioned suite will include three dashboards: an overarching "Platform Observability Overview" plus two deep-dive dashboards ("Application Logs Dashboard" and "Distributed Traces Dashboard").
- **Q2: Default Landing Experience**: User selected Option A. OpenSearch Dashboards will be configured to load the "Application Logs Dashboard" directly by default upon startup.
- **Q3: Default Time Window & Auto-Refresh**: User selected Option A. Dashboards will be pre-configured with a 15-minute rolling time window and 10-second auto-refresh.

---

### Key Entities

- **Index Pattern**: Saved object defining an OpenSearch index or data stream pattern (`otel-logs*`, `ss4o_traces-*`), its primary timestamp field, and field data types.
- **Observability Dashboard**: Container saved object assembling multiple visualization panels, search queries, time range controls, and data tables into a cohesive single-pane view.
- **Visualization Panel**: Individual graphical or tabular widget (e.g., bar chart, pie chart, metric counter, or data table) bound to an index pattern and aggregation query.
- **Provisioning Manifest / Payload**: Pre-packaged export file containing the serialized definitions of index patterns, visualizations, and dashboards imported during startup.

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of defined dashboards (Logs and Traces) and index patterns are visible and queryable in OpenSearch Dashboards upon startup with zero manual developer intervention.
- **SC-002**: A developer opening the OpenSearch Dashboards interface can inspect correlated logs from any running microservice within 30 seconds of landing on the UI.
- **SC-003**: Provisioning completes within 30 seconds after OpenSearch reaches healthy status.
- **SC-004**: Re-running environment startup multiple times results in exactly 0 duplicate dashboards or index patterns.
- **SC-005**: Filtering by a service name or severity level refreshes all dashboard panels and data tables in under 2 seconds.

---

## Assumptions

- Docker Compose is the standard development deployment mechanism for running OpenSearch and OpenSearch Dashboards.
- OpenSearch is running with demo security disabled (`DISABLE_SECURITY_PLUGIN=true` and `DISABLE_SECURITY_DASHBOARDS_PLUGIN=true`) in the local development environment.
- Microservices stream logs to `otel-logs` and traces to `ss4o_traces-*` via the OpenTelemetry Collector as established in Feature 011.
- OpenSearch Dashboards REST API (Saved Objects API) or provisioning scripts are accessible via the internal Docker network.
- The entrypoint wrapper script `infrastructure/opensearch-dashboards/entrypoint-wrapper.sh` MUST be granted executable permissions (`chmod +x` / mode `0755`) so Docker can execute it directly on container startup without permission errors.
